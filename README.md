# Козёл — исправленная версия 0.0.2

Исходная версия: архив `kozel-main.zip` (commit c9219efbcd9840b5dadb80e59f0038365b8cba6e). Изменения по девяти пунктам `kozel_plan.pdf`. Старые обсуждения и правила не использованы. Колода 36 карт, раздача по 6, смена козыря, порядок штрафных баллов, порог 24 и текущий принцип завершения взятки сохранены. Внешний вид в основном сохранён, добавлены статусы мест игроков и копирование ID комнаты.

## Важно перед выкладкой

1. **Смените ранее опубликованный пароль PostgreSQL и JWT-секрет.** Старые значения больше не используйте. Удаление из новых исходников не удаляет секреты из истории Git. Отзовите старые ключи на хостинге и проверьте историю репозитория, доступ к базе, журналы и резервные копии. Новый JWT-секрет завершит старые сессии, игрокам понадобится повторный вход.
2. Сделайте резервную копию базы. Сначала запускайте эту версию на отдельной тестовой БД. Миграция добавляет уникальный индекс по `lower(username)` и таблицу учёта матчей `settled_matches`, приводит последовательность ID в соответствие с существующими записями. Если имеются дубли ников без учёта регистра, запуск остановится до ручного разрешения конфликтов — аккаунты автоматически не объединяются и не удаляются.
3. Удалите из репозитория старые `server-dist/`, `packages/game-core/dist/`, скомпилированные JS-файлы из `packages/game-core/src/` и `tests/`, `apps/server/users.json`, старые lock-файлы и пустые копии `.txt`. Просто загрузка нового содержимого поверх старого в GitHub не удаляет устаревшие файлы. Архив содержит новый исходный проект целиком; исходный архив не изменён.
4. Не публикуйте реальные `.env`, пароли или резервные копии пользователей.

## Запуск локально

Нужны Node.js 22+, pnpm 10.11.0 и отдельная PostgreSQL (например, база `kozel_test`). В корне проекта:

```sh
corepack enable
corepack prepare pnpm@10.11.0 --activate
pnpm install --no-frozen-lockfile
pnpm test
pnpm build
```

Старый `pnpm-lock.yaml` не соответствовал зависимостям и удалён. При первой установке pnpm должен создать новый; **добавьте новый lock-файл в Git**. Следующие установки можно выполнять с `--frozen-lockfile`. Установка и новая фиксация версий в среде аудита не были возможны из-за отсутствия доступа к npm-реестру.

Скопируйте `apps/server/.env.example` в `apps/server/.env`, а `apps/client/.env.example` в `apps/client/.env`. Заполните новый `DATABASE_URL`, `JWT_SECRET` (не менее 32 символов), `CORS_ORIGINS`. Случайный секрет можно создать командой:

```sh
node -e "console.log(require('node:crypto').randomBytes(48).toString('hex'))"
```

Локальный сервер без TLS: `DB_TLS=disable` (только для тестовой базы на локальной машине). В рабочей среде используйте проверенный TLS (`DB_TLS` не указывать или указать значение, отличное от `disable`). Для частного центра сертификации задайте `DB_CA` с PEM-сертификатом. `NODE_ENV=production` запрещает отключённый TLS. `ADMIN_USER_IDS` — идентификаторы **существующих доверенных** учётных записей через запятую; пустое значение отключает административные права. Получите идентификатор в своей базе (`SELECT id, username FROM users;`). Никнейм больше не назначает роль.

В двух терминалах из корня проекта:

```sh
pnpm dev:server
pnpm dev:client
```

Откройте `http://localhost:5173`. При игре с телефона укажите `VITE_API_URL` с адресом сервера, достижимым с телефона, и включите точный адрес клиентского сайта в `CORS_ORIGINS`. После изменения `VITE_API_URL` пересоберите клиент.

## Публикация на хостинге

- Сборка клиента: `pnpm --filter @kozel/client build`, результат `apps/client/dist`. `VITE_API_URL` должен содержать HTTPS-адрес вашего сервера, а `CORS_ORIGINS` на сервере — HTTPS-адрес клиента.
- Из корня: `pnpm install --no-frozen-lockfile` (первый запуск), затем `pnpm build`. Запуск серверного исходника: `pnpm --filter @kozel/server start`.
- Если старый хостинг развёртывал только `server-dist`, выполните `pnpm build:deploy`. Команда генерирует новый самостоятельный сервер и его `package.json`, без встроенных секретов. В каталоге `server-dist` установите production-зависимости и запустите `npm start`. Старую сборку не используйте.
- Изменения в сервере и клиенте должны быть выложены вместе: новый сервер проверяет версию игрового состояния, а клиент отправляет её с каждым игровым действием. Вход по старым JWT будет недоступен после смены секрета.
- Настройте переменные окружения через панель хостинга, не в Git. Точная конфигурация действующего хостинга в исходном архиве отсутствует.

## Проверки

`pnpm test` — тесты движка (Node test runner). `pnpm test:db` — интеграционные тесты PostgreSQL, только если `KOZEL_TEST_DATABASE_URL` указывает на отдельную базу с именем, заканчивающимся `_test`. `pnpm test:integration` — HTTP и Socket.IO, только при указании локального `KOZEL_TEST_SERVER_URL` и запущенном сервере, подключённом к тестовой БД. Тесты добавляют тестовые аккаунты; не запускайте их на рабочих данных. `.github/workflows/verify.yml` запускает проверки, сборку и временный PostgreSQL в GitHub Actions. После загрузки проекта проверьте вкладку Actions.

Фактически выполнено в среде исправления: строгая компиляция TypeScript игрового ядра, 12 тестов (включая 200 полных симуляций конов, 100 для каждого режима), проверка синтаксиса 16 TS/TSX-файлов клиента, сервера и DB-теста, синтаксис JS-скриптов. Все перечисленные выполненные проверки прошли. Полная сборка клиентского и серверного приложений, установка зависимостей, реальные HTTP/Socket.IO и PostgreSQL тесты и запуск в мобильном браузере **не выполнены**. Они требуют сетевого доступа к npm и тестовой инфраструктуры. Не выкладывайте на рабочий сервер до зелёного CI и ручной проверки.

## Принятые решения и оставшиеся ограничения

- Пустая атака запрещена. Пустой сброс первоначального атакующего при возвращении очереди сохранён по явному поведению текущего интерфейса; другим игрокам нужно сбросить нужное количество карт либо весь остаток, если его меньше. Это решение необходимо подтвердить игровым тестом. Допустимые ответные комбинации совпадают с `canBeat`, в том числе смешанные масти, если все карты могут перебить стол. Принцип завершения взятки после первого паса в 2×2 оставлен как в текущем движке — это не прежние правила.
- При разрыве сети место восстанавливается по аутентифицированному аккаунту; автоматический ход продолжает игру. Комнаты хранятся в памяти одного серверного процесса. После перезапуска сервера текущие матчи не восстановятся; горизонтальное масштабирование на несколько процессов потребует общего хранилища и Socket.IO adapter. Неактивные комнаты удаляются спустя 30 минут без действий пользователя.
- Результаты матчей сохраняются транзакционно и идемпотентно по уникальному ID матча. При временной ошибке записи сервер повторяет сохранение, пока работает. Если сервер аварийно завершится до записи, несохранённый результат может быть потерян. Тренировочные DEV-матчи не записываются в рейтинговую статистику, чтобы нельзя было накручивать победы.
- Ограничение входа и регистраций — 10 попыток за 15 минут на IP в одном серверном процессе; для публичного кластера нужен общий rate limiter и доверенная конфигурация reverse proxy. Существующие короткие пароли принимаются для старых аккаунтов, новые пароли — от 8 символов. Рекомендуется сменить старые слабые пароли; автоматический сброс паролей в этом проекте не реализован.
- Старый дизайн не переделывался; мобильную верстку, 3D-графику и соединение через действующий хостинг нужно проверить на реальных устройствах.
